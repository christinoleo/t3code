# Self-improving software factories

Research on how systems of autonomous coding agents improve their own process, instructions, tools and guardrails, and what that means for the maestro factory in this repo. Read on 2026-11-28 from papers, vendor engineering posts and docs, and the source PDFs where the HTML was cut. A claim marked **UNVERIFIED** comes from a search snippet, a README or a secondary summary, not from text I read in the primary source.

The factory this is for: a dispatcher hands GitHub issues to a builder ([`maestro-worker`](../workflow/skills/ak/maestro-worker/SKILL.md)), then to a separate reviewer that fixes and merges ([`maestro-reviewer`](../workflow/skills/ak/maestro-reviewer/SKILL.md)). It improves itself through the reviewer's mistake log (a class caught twice gets fixed in the same PR, by a lint, a test or a row in the "Mistake rules" table of [`CLAUDE.md`](../CLAUDE.md)), an end-of-epic `retro`, and `automate-me` updating the user's mode skill ([`maestro`](../workflow/skills/ak/maestro/SKILL.md)). Nothing measures the factory itself.

## Short answer

- Every self-improvement result that holds up closes its loop on an **external, checkable signal**: tests, a benchmark score, a verifier. Reflection without one does not reliably help, and can hurt ([Huang et al. 2023](https://arxiv.org/abs/2310.01798)). Measurement comes first. The self-modifying agents (DGM, SICA, AlphaEvolve, AHE) are all built around an evaluator. The production builders (OpenAI, Anthropic) all describe reading traces and running evals before changing the harness.
- What works across tasks is **curated, incremental, evidence-carrying memory**. It is a list of lessons that each carry counters, citations or an expiry, updated by small deltas. Rewriting the whole file each time is what fails ([ExpeL](https://arxiv.org/abs/2308.10144), [ACE](https://arxiv.org/abs/2510.04618), [Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)).
- **Turning a repeated mistake into a mechanical check** is the most consistent finding, from Toyota through Google SRE to OpenAI's Codex team. A rule written as prose is weaker, and long instruction files measurably cost money and attention ([Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988), [IFScale](https://arxiv.org/abs/2507.11538)).
- The main failure modes are objective hacking, context bloat or collapse, and action items piling up faster than they close. Each is documented with numbers. The gates that work are a hidden or independent grader, regression evals, an archive for rollback, and a human approving changes to shared instructions.
- For maestro, the evidence **supports** the separate reviewer, fixing in the same PR, and not auto-filing tickets. It **argues against** running with no measurement and against the Mistake rules table growing without pruning in every agent's context.

## Loop 1: within one task

### Verbal reflection on grounded feedback (Reflexion, Self-Refine)

- **Reflexion** turns scalar or binary feedback from the environment into a written reflection, and keeps it in an episodic memory for the next attempt ([Shinn et al. 2023](https://arxiv.org/abs/2303.11366)). It reports 91% pass@1 on HumanEval against 80% for GPT-4 alone, and +22% absolute on AlfWorld in 12 iterations ([abstract](https://arxiv.org/abs/2303.11366)). The coding gain depends on self-generated unit tests as the feedback signal ([paper](https://arxiv.org/abs/2303.11366)).
- **Self-Refine** has one model generate, critique and revise its own output. It reports about 20 points absolute average gain over single-pass generation across 7 tasks ([Madaan et al. 2023](https://arxiv.org/abs/2303.17651)).
- **The limit:** "LLMs struggle to self-correct their responses without external feedback, and at times, their performance even degrades after self-correction" ([Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798)). Reflection pays off when something outside the model, such as tests, a compiler or a grader, says what went wrong.

### Watch the run as it happens (SICA's overseer, Anthropic's progress files)

- SICA runs an LLM **overseer** "periodically in a concurrent thread", "every 30s by default, or on key events". It looks for "pathological behaviours or deviations from the original task". It can send a steering notification into the agent's context or cancel it, and must "make at least one attempt to notify the agent" before cancelling ([SICA §3.1, App.](https://arxiv.org/abs/2504.15228)). The paper gives no ablation of the overseer.
- For work spanning several context windows, Anthropic keeps a progress file (`claude-progress.txt`) next to git history, so a fresh session can see the state of the work ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). This is **UNVERIFIED** beyond the search excerpts.

## Loop 2: across tasks and epics (experience, memory, postmortems)

### Insight lists with votes (ExpeL)

ExpeL gathers successful and failed trajectories, then has an LLM maintain a list of cross-task insights with **ADD, UPVOTE, DOWNVOTE and EDIT** operations. The list is used in the prompt with no weight updates ([Zhao et al., AAAI-24](https://arxiv.org/abs/2308.10144)). The votes matter because an insight that keeps getting downvoted drops out, so the list does not only grow.

### Verified skill libraries (Voyager, Agent Workflow Memory)

- **Voyager** commits a program to its skill library only after "a self-verification module confirms the task completion" ([Wang et al. 2023](https://arxiv.org/abs/2305.16291)). It reports 3.3× more unique items and tech-tree milestones up to 15.3× faster than the prior state of the art ([arXiv abstract](https://arxiv.org/abs/2305.16291); the NeurIPS listing says 3.1×). Removing self-verification costs 73% of discovered items. Without the skill library the agent plateaus ([paper, ablations](https://arxiv.org/abs/2305.16291)).
- **Agent Workflow Memory** induces reusable workflows from past successful trajectories. It reports +51.1% relative success on WebArena and +24.6% on Mind2Web, with about 2 fewer steps per task ([Wang et al., ICML 2025](https://arxiv.org/abs/2409.07429)).

### Incremental context, not rewrites (ACE)

[Agentic Context Engineering](https://arxiv.org/abs/2510.04618) names two failure modes of self-edited instructions:

- **Brevity bias:** "the tendency of optimization to collapse toward short, generic prompts" (§2.2).
- **Context collapse:** when an LLM rewrites the whole accumulated context at each step, it produces "much shorter, less informative summaries." On AppWorld the context went from 18,282 tokens at 66.7% accuracy to 122 tokens at 57.1%, below the 63.7% no-adaptation baseline (§2.2).

ACE's fix is **delta updates**. A curator emits small new bullets, "merged deterministically into the existing context by lightweight, non-LLM logic". Existing bullets are updated in place, for example by incrementing counters, and a dedup pass prunes redundancy (§3). It reports +10.6% on agent tasks, +8.6% on finance, and 86.9% lower adaptation latency ([abstract, §4](https://arxiv.org/abs/2510.04618)).

### Production memory with a human or a validity check in the loop (Devin, Copilot)

- **Devin** suggests new Knowledge from chat feedback, and a human edits it before saving or dismisses it ([Devin docs: Knowledge](https://docs.devin.ai/product-guides/knowledge)). Devin can analyse "why a session succeeded or failed" and compare successes with failures "to propose targeted improvements" to skills. The docs suggest a weekly schedule to "review pending knowledge suggestions, deduplicate entries, and resolve conflicting guidance" ([Advanced capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities)). Knowledge is now deprecated in favour of Skills ([same page](https://docs.devin.ai/product-guides/knowledge)).
- **GitHub Copilot Memory** stores each memory with citations to the code that supports it. It checks those citations against the current code before using the memory, and deletes a memory unused for 28 days ([GitHub docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory), [changelog](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/)).

### Postmortem action items (Google SRE)

This literature is about what this repo calls the retro, and it is the most direct evidence on why improvement work piles up.

- Classify action items as **Investigate, Mitigate, Repair, Detect, Prevent**, and word each one **actionable, specific and bounded**. Bounded means "indicate how to tell when it is finished". Prefer "automated fixes when possible, as opposed to prevention/mitigation that requires ongoing manual intervention" ([Lunney, Lueder & Beyer, ;login: 2017](https://www.usenix.org/publications/login/spring2017/lunney)).
- **Piling up is the documented failure.** "The most common shortcoming is lack of follow-up." Google tracks action items "created vs. closed by day", and "the widening distance between the two lines indicates accumulating technical debt". Outstanding P1 items had been open "almost as long as outstanding P3 AIs". The advice is to close items "you'll never have time to address—don't keep them around forever" ([same](https://www.usenix.org/publications/login/spring2017/lunney)).
- **Overfitting a fix:** "We rarely repeat incidents, but we sometimes have incidents that rhyme." Considering one incident in isolation "may overfit a specific solution". "Overly specific monitoring changes" only help "if that very specific failure mode recurs in the exact same way (which is frequently not the case)" ([same](https://www.usenix.org/publications/login/spring2017/lunney)).
- "Trying to change human behavior is less reliable than changing automated systems and processes." "Without a formal tracking process, action items from postmortems are often forgotten" ([SRE Workbook ch. 10](https://sre.google/workbook/postmortem-culture/)).

### Stop the line and fix the cause (Toyota)

Jidoka is "stopping immediately when abnormalities are detected", with an operator able to "stop the line by pulling the stop cord". Stopping makes it "possible to build quality into processes by clearly detecting abnormalities and preventing them from recurring" ([Toyota, TPS](https://global.toyota/en/company/vision-and-philosophy/production-system/)). I found no Toyota page on poka-yoke or on stop frequency falling over time, so those parts are **UNVERIFIED** from Toyota's own sources. Google's SRE article does recommend five-whys root cause analysis ([Lunney et al.](https://www.usenix.org/publications/login/spring2017/lunney)).

### Promote review feedback into tooling (OpenAI's Codex team)

OpenAI's "harness engineering" post is the closest published analogue to maestro. It describes three engineers, later seven, merging about 1,500 agent PRs, at 3.5 PRs per engineer per day ([OpenAI, Feb 2026](https://openai.com/index/harness-engineering/)).

- "Review comments, refactoring pull requests, and user-facing bugs are captured as documentation updates or encoded directly into tooling." "When documentation falls short, we promote the rule into code."
- Custom lints carry the fix: "we write the error messages to inject remediation instructions into agent context."
- Recurring cleanup replaced a manual tax. "Our team used to spend every Friday (20% of the week) cleaning up 'AI slop.'" Now background Codex tasks run "on a regular cadence" to scan for deviations and open refactoring PRs, which "can be reviewed in under a minute and automerged". A "doc-gardening" agent fixes stale docs.
- When the agent struggles: "identify what is missing—tools, guardrails, documentation."
- Caveat from the post: it "should not be assumed to generalize", and the team does not yet know "how architectural coherence evolves over years".

## Loop 3: the harness itself (instructions, tools, the agent's own code)

### Prompt and instruction optimization against a metric

Each of these needs a scored dataset to optimize against.

| Method                                         | What it changes                                                             | Reported result                                                                                                     |
| ---------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| [OPRO](https://arxiv.org/abs/2309.03409)       | Instruction text, proposed by an LLM from past (prompt, score) pairs        | Up to +8 on GSM8K and +50 on Big-Bench Hard over human prompts (maxima, not typical)                                |
| [DSPy](https://arxiv.org/abs/2310.03714)       | Demonstrations and instructions of a declared pipeline                      | About +25% (GPT-3.5) and +65% (Llama2-13b) over few-shot prompting                                                  |
| [TextGrad](https://arxiv.org/abs/2406.07496)   | Any text variable, using LLM critiques as "gradients"                       | 20% relative gain on LeetCode-Hard; GPQA 51% → 55%                                                                  |
| [GEPA](https://arxiv.org/abs/2507.19457)       | Prompts, by reflective mutation with a Pareto front per instance            | Beats GRPO by 6% on average (up to 20%) with up to 35× fewer rollouts; beats MIPROv2 by over 10% (v2 numbers)       |

GEPA's Pareto front keeps the best prompt for each problem instance, not only one global best ([abstract](https://arxiv.org/abs/2507.19457)). That is the same idea as DGM's archive below.

### Agents that rewrite their own scaffold

- **STOP** has a seed "improver" program improve itself with GPT-4. The model proposed beam search, genetic algorithms and simulated annealing. The authors note it is not full recursive self-improvement because the model is unchanged, and they measure how often generated code tries to bypass a sandbox ([Zelikman et al., COLM 2024](https://arxiv.org/abs/2310.02304)). The exact bypass rate is **UNVERIFIED**.
- **SICA** edits its own codebase. Its utility weighs score 0.5, cost 0.25 (capped at $10 per problem) and time 0.25 (capped at 300 s), with a 0.5 penalty for timeouts. The best agent in the archive becomes the next meta-agent ([Robeyns et al. 2025, Eq. 1–2](https://arxiv.org/abs/2504.15228)). It reports 17% → 53% on a fixed 50-problem subset of SWE-bench Verified. Table 1 ends at 51% at iteration 15. LiveCodeBench moved 65% → 71%, and cost per problem fell from $1.91 to $1.70. The 14 improvements it made were almost all **tools**: a diff-based smart editor, an AST symbol locator, a ripgrep context summariser and file-size limits (App. D). Reasoning tasks barely improved. The 15-iteration run cost about $7,000 ([§4–5](https://arxiv.org/abs/2504.15228)).
- **Darwin Gödel Machine (DGM)** keeps an **archive** of every agent variant and samples parents "roughly proportional to each agent's performance score and inversely proportional to the number of its children". It reports 20.0% → 50.0% on SWE-bench and 14.2% → 30.7% on Polyglot ([Zhang et al., ICLR 2026](https://arxiv.org/abs/2505.22954)). Discovered changes include line-range viewing, string-replacement editing, "making multiple attempts … and using another FM to evaluate and select the best solution", and considering previous attempts (§4). Both ablations underperform, with no self-improvement of the meta-agent and with no archive. Without the archive, "a poorly performing self-modification makes subsequent improvements harder to achieve" (§4). Improvements transferred across models and benchmarks (§4). One SWE-bench run cost about USD 22,000 (App. E.1).
- **AlphaEvolve** (Google DeepMind) evolves code against automated evaluators. One evolved Borg scheduling heuristic "continuously recovers, on average, 0.7% of Google's worldwide compute resources" and had been in production over a year ([DeepMind blog](https://deepmind.google/discover/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)). DeepMind scopes it to domains "where progress can be clearly and systematically measured" ([same](https://deepmind.google/discover/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)).
- **Agentic Harness Engineering (AHE)** argues the bottleneck in harness evolution is observability, not the evolving agent. It exposes each harness part as a file, condenses traces into layered evidence, and adds **decision observability**: each edit is tied to a prediction that the next round checks ([Lin et al. 2026](https://arxiv.org/abs/2604.25850)). The reported Terminal-Bench 2 gain, 69.7% → 77.0% over ten iterations, comes from the [project README](https://github.com/china-qijizhifeng/agentic-harness-engineering) and is **UNVERIFIED** against the paper body.

### What production builders publish

- **Anthropic, tools:** build an eval, then "use Claude Code to automatically optimize your tools against this evaluation"; concatenate eval transcripts and have Claude analyse them ([Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). In the research system, a tool-testing agent rewrote a flawed tool's description after testing it "dozens of times". That gave "a 40% decrease in task completion time for future agents using the new description" ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Evals started with "about 20 queries representing real usage patterns", and "people testing agents find edge cases that evals miss" ([same](https://www.anthropic.com/engineering/multi-agent-research-system)).
- **Anthropic, evals:** "20-50 simple tasks drawn from real failures is a great start." Capability evals start at a low pass rate. Once they pass reliably they "'graduate' to become a regression suite that is run continuously". "You won't know if your graders are working well unless you read the transcripts." pass^k, the probability that all k trials succeed, measures reliability: 75% per trial gives about 42% for three in a row. Grader bugs mislead badly: Opus 4.5 "initially scored 42% on CORE-Bench" and reached 95% after grading fixes ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
- **Anthropic, context:** context is "a finite resource with diminishing marginal returns"; aim for "the smallest possible set of high-signal tokens" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Claude Code's docs say each CLAUDE.md line "takes a little of Claude's attention on *every* task", recommend staying under 200 lines, and say a line that keeps being missed despite emphasis "belongs in a hook". A hook is deterministic, "for a rule with *zero* exceptions" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)).
- **OpenAI:** a short `AGENTS.md` of "roughly 100 lines" that "serves primarily as a map", with the rest in `docs/`. The single big instruction file failed because "it rots instantly" and "too much guidance becomes non-guidance" ([Harness engineering](https://openai.com/index/harness-engineering/)).
- **Cognition (Devin):** session analysis and human-approved knowledge suggestions, above.
- **Factory.ai:** scores repositories on "agent readiness" across eight pillars and five levels. `/readiness-fix` proposes changes for failing signals, and the docs tell you to review them and "commit only what looks good" ([Factory docs](https://docs.factory.ai/agent-readiness/overview)). This is from search excerpts and is **UNVERIFIED** beyond them.
- **GitHub Copilot coding agent:** Actions workflows on its PRs need approval from someone with write access before they run, and the agent runs behind a firewall by default ([GitHub docs](https://docs.github.com/en/copilot/responsible-use/copilot-coding-agent)). Memory validation is above.
- **Sourcegraph/Amp:** I found no primary Amp post on improving its harness from traces or evals. Its docs only describe how `AGENTS.md` files load ([Amp docs](https://ampcode.com/docs/customize/agents-md)).

### Measuring the delivery system (DORA, error budgets)

- DORA now uses five metrics. Throughput is change lead time, deployment frequency and failed-deployment recovery time. Instability is change fail rate and deployment **rework rate** ([dora.dev](https://dora.dev/guides/dora-metrics-four-keys)).
- DORA 2024 associates each 25% rise in AI adoption with an estimated −1.5% delivery throughput and −7.2% delivery stability. This is a survey correlation ([2024 DORA report PDF](https://services.google.com/fh/files/misc/2024_final_dora_report.pdf), [Google Cloud announcement](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)). It is **UNVERIFIED** against the report text; the figures come from Google's announcement and coverage.
- An SRE error budget policy halts "all changes and releases other than P0 issues or security fixes" when the budget is spent. An incident consuming over 20% of the budget requires a postmortem with "at least one P0 action item" ([SRE Workbook, error budget policy](https://sre.google/workbook/error-budget-policy/)). It turns a measured threshold, rather than someone's judgement on the day, into the trigger for reliability work.

**How sources gate a self-change, in short.** Research systems gate on a held-out benchmark score plus an archive for rollback (DGM, SICA, AlphaEvolve). Production builders gate on a regression eval, reading transcripts, and a human approving changes to shared instructions or memory (Anthropic, Devin, Factory). OpenAI automerges small agent cleanup PRs because humans can review each one "in under a minute". None of the production sources lets an agent change its own instructions with no check at all.

## What fits maestro

### Current pieces the evidence supports

- **A separate reviewer that did not build the PR.** This matches graders independent of the thing graded (DGM's hidden checker, Anthropic's isolated judges) and OpenAI's agent-to-agent review.
- **Fixing a repeated class in the same PR.** This is jidoka: stop and fix the cause at the line ([Toyota](https://global.toyota/en/company/vision-and-philosophy/production-system/)). Waiting for two catches before fixing matches the "incidents that rhyme" advice and avoids one-off overfitting ([Lunney et al.](https://www.usenix.org/publications/login/spring2017/lunney)).
- **Never filing tickets from the log, and leaving hardening to a human at the retro.** The created-vs-closed gap is the documented failure of follow-up work ([Lunney et al.](https://www.usenix.org/publications/login/spring2017/lunney)). Production memory systems put a human or an expiry in the loop ([Devin](https://docs.devin.ai/product-guides/knowledge), [Copilot](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). The earlier auto-ticket loop that grew guards about guards is the runaway meta-work every source warns about.
- **`automate-me` showing its proposed change before it lands.** This is Devin's approve-or-dismiss knowledge suggestion.

### Current pieces the evidence argues against

- **No measurement of the factory.** Every working loop above has a metric: SICA's score/cost/time utility, DGM's benchmark, AHE's trace evidence, DORA, error budgets, action-item burndown. The 25% duplicate-check finding came from one manual timing pass, which shows how much is invisible without it.
- **"One small local rule" as an equal option to a lint or test, and a Mistake rules table that only grows.** Prose rules are the weakest fix: "changing automated systems" beats changing behaviour ([SRE Workbook](https://sre.google/workbook/postmortem-culture/)). A repeatedly missed line "belongs in a hook" ([Claude Code](https://code.claude.com/docs/en/best-practices)). Every CLAUDE.md line costs attention on every task, and context files raise cost by over 20% ([Gloaguen et al.](https://arxiv.org/abs/2602.11988)). The table has no removal path, which is ExpeL without DOWNVOTE and Copilot memory without expiry.
- **`automate-me` regenerating a skill from chat history.** If it rewrites the mode skill wholesale, it risks context collapse ([ACE](https://arxiv.org/abs/2510.04618)). LLM-written context files slightly lowered success ([Gloaguen et al.](https://arxiv.org/abs/2602.11988)). Edits should be deltas the user approves.

### The techniques with the best evidence, mapped onto maestro

Each entry gives the technique, why it is worth trying, and the smallest change that would try it.

1. **Measure each step (SICA's utility, AHE's experience observability, DORA).** The dispatcher already knows when each worker and reviewer starts and ends. *Smallest change:* have the dispatcher append one line per finished step (issue, role, start, end, outcome, retry count, check runs, token cost if the harness reports it) to a log. Compute time per step, retries per issue, stalls and rework rate (PRs reopened or followed by a fix) at each retro. No fixes until a week of data exists.
2. **Turn a twice-caught class into a mechanical check by default, with the fix in the error message (OpenAI's lints, SRE's "automated fixes", Claude Code's hooks).** *Smallest change:* in "Log what you caught" step 3, make a lint or test the default and a rule-table row the fallback only when no check can express it. Have the lint message say what to do instead, so the agent that trips it is told the fix.
3. **Give every rule a counter, a date and a way out (ExpeL votes, ACE counters and dedup, Copilot's 28-day expiry, SRE's "close what you'll never do").** *Smallest change:* add a "last caught" date column to the Mistake rules table, updated when the reviewer logs a catch of that class. At each retro, delete or demote any row not caught in N epics, and merge duplicates. Edit rows one at a time and never regenerate the table.
4. **Check that a self-change worked (AHE decision observability, Anthropic's regression evals, DGM's archive and rollback).** *Smallest change:* when a PR changes a maestro skill or a Mistake rules row, put one predicted effect in its body, such as "duplicate check runs per PR drop to ~0". The retro checks it against technique 1's log and reverts changes that did not deliver. A replay set of 20–50 past issues ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)) is the stronger version. It costs agent runs, so whether to build it is a budget call for Leo.
5. **Write retro outputs as bounded action items and watch created vs closed (Lunney et al.).** *Smallest change:* each retro action item starts with a verb, says how to tell it is done, and has an owner (Leo or "maestro"). The retro opens by counting the previous retros' items created vs closed. It closes stale ones instead of carrying them.
6. **Keep the grader out of the builder's reach and read transcripts (DGM App. H, METR, Anthropic).** The known hack is editing tests or scoring code. *Smallest change:* in review step 5, the reviewer reads diffs to existing tests, lints and CI config as suspect by default, and justifies any loosening in the PR. At each retro, read one full builder transcript at random, not only the diff.
7. **Let a measured threshold, not a ticket generator, trigger factory work (SRE error budgets, jidoka).** This replaces the abandoned auto-ticket loop with something bounded. *Smallest change:* once technique 1 exists, Leo picks one threshold, such as retries per issue over a 2-week window. When it is crossed, the dispatcher's daemon reports it once (as it already reports a stuck queue), and the next retro is about the factory. Nothing gets filed automatically.

### Not worth trying yet

- Full self-modification in the style of DGM, SICA or AlphaEvolve. These systems need a benchmark the factory can run on every variant, and runs cost $7,000–$22,000 ([SICA](https://arxiv.org/abs/2504.15228), [DGM](https://arxiv.org/abs/2505.22954)).
- Prompt optimizers such as DSPy, GEPA or OPRO. They need a scored dataset, so they only become possible after techniques 1 and 4.
