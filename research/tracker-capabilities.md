# Tracker capabilities for a tracker-neutral software factory

Research for [#38](https://github.com/christinoleo/t3code/issues/38), a child of the map [#35](https://github.com/christinoleo/t3code/issues/35). Read on 2026-11-27 from each tracker's official docs, API specs or source. A claim marked **UNCONFIRMED** has no primary source behind it.

The question: how does each tracker `IssueService` supports express parents, blocked-by, workflow states, assignment as a claim, conditional writes for claim races, and change feeds? What can a neutral factory model rely on, and what must it emulate?

## What the drivers use today

- The port is `IssueTrackerApi` in [`packages/source-control-core/src/server/IssueTracker.ts`](../packages/source-control-core/src/server/IssueTracker.ts). It covers list, get, comments, create, comment, update (title, body, labels, assignees), `setState`, reactions, templates and candidates. **It has nothing for parents, relations, claims or change feeds.**
- `IssueCapabilities` in [`packages/contracts/src/issue.ts`](../packages/contracts/src/issue.ts) flags create, edit, comment, labels, assignees, reactions, templates, linkedPullRequests, events and search. Labels and assignees are written as **whole-set replacements** ("which is how every tracker writes them"), so two writers can lose each other's edits.
- [`apps/server/src/issue/IssueTrackerRegistry.ts`](../apps/server/src/issue/IssueTrackerRegistry.ts) joins the git-host drivers with the two standalone trackers (Linear, Jira).

| Tracker         | Transport in the driver             | States `setState` offers                                                                                                    |
| --------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| GitHub          | GraphQL, plus REST for closing      | Open/closed with a close reason. On github.com it also offers the repository's preview issue statuses (`planningStatuses`). |
| GitLab          | `glab api` (REST, one GraphQL path) | Open/closed (`state_event`)                                                                                                 |
| Forgejo         | `ForgejoCli.api` (REST)             | Open/closed                                                                                                                 |
| Azure DevOps    | `az boards` and `az devops invoke`  | Every state of the work item type                                                                                           |
| TanStack Source | REST at `/api/v1`                   | Open/closed                                                                                                                 |
| Linear          | GraphQL with an API key             | Every workflow state of the team                                                                                            |
| Jira Cloud      | REST v3 with an API token           | Only the transitions available from the current status                                                                      |

Each driver maps HTTP 429 or its CLI's rate-limit error to `IssueTrackerError.reason = "rate-limited"`. Some also carry a `retryAt`.

## Per-capability findings

### Parents

Five of seven trackers have a native parent: GitHub, GitLab, Azure DevOps, Linear and Jira. Forgejo and TanStack Source have none.

Even the native ones disagree:

- Azure DevOps and GitLab allow **one parent** and a fixed type ladder. GitLab runs epic → issue → task, and nested epics need Ultimate.
- Jira subtasks must stay in the parent's project.
- GitHub allows 100 children and 8 levels, across repositories.
- Linear is the loosest: cross-team, no documented depth limit.

### Blocked-by

Native and usable on GitHub, Forgejo, Azure DevOps, Linear and Jira. GitLab has it on Premium only. TanStack Source has none.

- **Only Forgejo enforces it**: closing a blocked issue returns 412.
- The rest treat it as metadata. GitLab says outright that a blocked item can still be closed.
- Jira's "Blocks" link type is admin-configurable and may not exist.
- Linear stores one direction (`blocks`), so a reader has to walk `inverseRelations` too.

### States

Only Azure DevOps, Linear and Jira have first-class custom workflow states, each mapped to a small fixed category set.

- GitLab's custom Status is Premium and GraphQL-only.
- GitHub's issue statuses are a fixed set of 7, in a preview that started on 2026-11-23, on github.com only.
- Forgejo and TanStack Source have open/closed only.

Labels exist everywhere. Labels that are **mutually exclusive by construction** exist on three trackers:

- Forgejo exclusive scopes
- GitLab scoped labels (Premium)
- Linear single-select label groups

A factory that encodes its lifecycle as one label per scope can rely on the server keeping only one value on those three. On the others it has to remove the old label itself.

### Assignment

Assignment exists everywhere. Linear, Jira and Azure DevOps hold one assignee. GitHub, Forgejo and TanStack Source hold many; GitLab holds many on Premium.

On a multi-assignee tracker, two claimants both "win", because adding is additive. GitHub also **silently ignores** an assignee change from a caller without push access.

Assignment is therefore a **visible marker, not a lock**. Linear also has a separate `delegate` slot meant for agents.

### Conditional writes

Only **Azure DevOps** has a real compare-and-set: JSON Patch `test /rev`. Jira comes close: a transition out of a specific status fails once another writer has moved the issue, though only officially "invalid for any other reason". Linear's batch update is atomic but not conditional.

GitHub, GitLab, Forgejo and TanStack Source have **no conditional write at all**. Every whole-set label or assignee write there is last-writer-wins. Four trackers offer additive label operations that avoid clobbering:

- GitHub "add labels"
- GitLab `add_labels`/`remove_labels`
- Linear `addedLabelIds`
- TanStack Source POST

The current contract does not use them.

### Change feeds

Every tracker offers some push mechanism: webhooks or service hooks, plus SSE on TanStack Source. None of them covers everything:

- Linear sends no event for relation changes.
- Forgejo appears to send no event for dependency changes.
- Jira dynamic webhooks need an OAuth or Connect app; an API token can only use admin webhooks.
- Deliveries can repeat and carry no ordering guarantee (Jira says so outright).

Polling is the common floor. TanStack Source is the exception, with no updated-since filter; its SSE stream with `Last-Event-ID` and `reset` frames fills that role. T3 already has a signed-webhook ingress with relay delivery for scheduled tasks ([`apps/server/src/scheduledTasks/webhookVerification.ts`](../apps/server/src/scheduledTasks/webhookVerification.ts), [`RelayDeliveryProof.ts`](../apps/server/src/scheduledTasks/RelayDeliveryProof.ts)), so a server behind NAT can receive tracker webhooks through T3 Connect.

### Rate limits

The budget for a polling factory per credential:

| Tracker                  | Budget per credential                          |
| ------------------------ | ---------------------------------------------- |
| Linear (API key)         | 2,500 requests/h                               |
| GitHub                   | 5,000/h, writes 80/min                         |
| GitLab.com               | 2,000/min                                      |
| Azure DevOps             | 200 TSTU per 5 min                             |
| Jira (API token)         | Burst limits only, 20 writes per 2 s per issue |
| Forgejo, TanStack Source | Effectively unpublished                        |

Linear's is the tightest. GitHub's ETag 304s are free, so conditional polling costs nothing there.

## Lowest common denominator

A neutral factory model can rely on these across all seven trackers:

1. **An issue with a stable key, title, body and URL**, plus open/closed. Every driver already provides these.
2. **Free-form labels**: read, set and filter. TanStack Source filters on one label server-side; the driver matches the rest itself.
3. **Comments with tracker-assigned ids and timestamps**, in server order. This is the only universally _ordered_ write.
4. **Assignment to at least one account.** Visible to humans, not exclusive.
5. **Polling for changes** (TanStack Source through its SSE stream), with 429 and `Retry-After` handling.

The model **cannot** rely on any of the following, natively, on every tracker:

- parents
- blocked-by links
- workflow states beyond open/closed
- exclusive labels
- a conditional write
- a complete change feed

## What has to be emulated, and where

| Need                                                                     | Native where                                                                                    | Emulate elsewhere with                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Claim and lease** (exclusive, expiring)                                | Nowhere as a lease. Azure `test /rev` and Jira's transition guard can arbitrate a single write. | **T3-side state** is the authority: a lease row in the T3 server's DB, in the style of `EffectOutbox` leases. The tracker carries a mirror for humans: an assignee and/or a `factory:claimed` label, plus a claim comment. If more than one T3 server can dispatch the same scope, the only portable tie-break is **the first claim comment by server order** after the last release. |
| **Factory lifecycle state** (ready, claimed, in review, needs-you, done) | Azure, Linear and Jira custom states; GitLab Status (P); GitHub statuses (preview, fixed 7)     | **T3-side state** is authoritative. Mirror it as scoped labels (`factory/<state>`), which are server-exclusive on Forgejo, GitLab (P) and Linear groups, and swapped by the client elsewhere. Map it to native state where a category fits; use open/closed only for terminal states.                                                                                                 |
| **Parent / epic membership**                                             | GitHub, GitLab, Azure, Linear, Jira                                                             | T3-side edges, mirrored natively where available. On Forgejo and TanStack Source use body text (`Parent: #n`), which wayfinder already writes.                                                                                                                                                                                                                                        |
| **Blocked-by edges**                                                     | GitHub, Forgejo, Azure, Linear, Jira (if the link type exists), GitLab (P)                      | T3-side edges. Mirror them natively where available; elsewhere use body text (`Blocked by #n`). Never trust native enforcement, which exists only on Forgejo.                                                                                                                                                                                                                         |
| **Change detection**                                                     | Webhooks or hooks on all; SSE on TanStack Source                                                | Webhooks are a **latency hint**, routed through the existing scheduled-task ingress and relay. A periodic **reconcile poll** is the truth. Relation changes (Linear) and dependency changes (Forgejo) are only seen by the poll.                                                                                                                                                      |

In short, the tracker is the **human-facing projection and intake**. Claims, leases, lifecycle and the dependency graph live in T3, and are written out to the tracker as labels, comments and native links where those exist. The built-in local tracker can then be the one tracker where the projection and the truth coincide.

## Side findings for the drivers

- **TanStack Source**: the driver's comment "Source keeps no update time" (`TanStackSourceIssueTracker.ts:43`) looks out of date. `/docs/rest` lists `updatedAt` on issue rows. Not verified against the live API.
- **TanStack Source**: the driver reads `Retry-After` only as seconds, so an HTTP-date value leaves `retryAt` unset (`TanStackSourceApi.ts:135-138`).
- **Azure DevOps**: the driver updates through `az boards work-item update`, which cannot send a `test /rev` op. Using the CAS needs a raw PATCH, for example through `az devops invoke`, which the driver already uses elsewhere.
- **Contract**: whole-set label and assignee writes race with each other. A factory writing labels concurrently with humans should use additive add/remove operations where they exist.
